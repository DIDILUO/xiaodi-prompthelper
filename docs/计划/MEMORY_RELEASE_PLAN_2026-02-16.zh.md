# 内存释放专项审查与修复计划（2026-02-16）

## 目标
- 只针对内存占用做专项优化，不改业务交互。
- 优先降低长会话与多图场景下的常驻内存。
- 保证功能等价：聊天、跑图、回传、历史记录不被破坏。

## 当前定位（高风险内存点）
1. `webui/src/App.jsx` 中多处持有大体积 `data:image/...;base64` 字符串：
- `uploadImages`
- `messages[].images`
- `generatedPreviewImages`

2. 会话列表与消息在启动时一次性加载到内存（含图片 Base64 时，峰值会明显上升）。

3. 运行态映射对象可能持续增长（如思考翻译缓存、展开状态映射等），缺少按消息集合回收。

4. Electron 与 WebUI 双端缓存并存：
- 渲染层内存中保留图片
- 主进程磁盘缓存保留图片
- 两者未形成“持有即释放”的单向策略

5. 开发模式本身有额外开销（HMR/source-map/React dev runtime），但不应掩盖业务内存泄漏。

## 修复分批（按收益与风险排序）

### P0（先做，低风险，立即见效）
1. 给临时映射做自动回收：
- `thinkingTranslationMap`
- `thinkingOpenMap`
- 其他按 messageId 索引的状态

2. 图片状态生命周期收紧：
- 请求结束后尽快清理不再需要的中间数组引用
- 避免同一图片在多个 state 中长时间重复持有

3. 增加内存采样日志（开发期）：
- 渲染层：`performance.memory`（可用时）
- 主进程：`process.memoryUsage()`
- 用于对比“修复前/后”曲线

### P1（中风险，高收益）
1. 会话持久化去 Base64 化：
- 会话消息中不再持久化完整 `dataUrl`
- 持久化 `cacheId / filePath / 元数据`
- 展示或重跑时按需回读（懒加载）

2. 图片单一真源策略：
- 以内存缓存或磁盘缓存之一为主，不双持
- UI 渲染只保留预览所需数据，原图走缓存引用

3. 旧会话懒加载：
- 会话列表先加载元信息
- 消息体按需加载，离开会话可回收

### P2（结构优化）
1. 统一缓存预算：
- 以“文件数量 + 总字节数 + TTL”三维约束缓存
- 超预算自动清理（LRU）

2. 跑图多图流程减少重复副本：
- 发送链路避免同图重复编码/复制
- 统一复用压缩结果与缓存条目

## 验收标准
1. 开发模式连续运行 30 分钟，常规聊天+跑图后内存曲线可回落，无持续爬升。
2. 多会话切换后不出现“会话越多占用越高且不回落”的现象。
3. 跑图返回多图后，切换会话/清空预览可看到内存释放趋势。
4. 所有功能行为保持等价（不丢图、不丢消息、不影响回传）。

## 实施顺序
1. 先完成 P0 并做一次对比采样。
2. 再做 P1 的会话去 Base64 化（这是主收益项）。
3. 最后统一缓存预算与清理策略（P2）。

## 本轮进度（2026-02-16）
- 已完成（P0）
  - `chatSessions` 的本地 `localStorage` 写入改为防抖，减少流式更新时频繁序列化导致的峰值占用。
  - 跑图队列任务执行后主动释放任务内图片引用，避免队列对象长期持有大体积 `dataUrl`。
  - 新增开发期内存采样链路：
    - 渲染层：`performance.memory`
    - 主进程：`process.memoryUsage()`（通过 `shell:memory-sample`）
- 已完成（P1.1 第一阶段）
  - Electron `chat-save`：会话图片落盘到 `chat-image-cache`，会话 JSON 不再持久化 `dataUrl`。
  - Electron `chat-load`：检测旧格式（含 Base64）会自动迁移到缓存引用并回写。
  - WebUI：仅在当前会话按 `cacheId` 回读图片，非当前会话会释放 `dataUrl` 以降低常驻内存。
- 已完成（P1.2 第二阶段，部分）
  - 生成预览图新增 `generated-cache-read` 回读链路，支持按需从磁盘缓存回读 `dataUrl`。
  - `generatedPreviewImages` 收敛为“当前预览图保留 dataUrl，非当前项优先释放为缓存引用”，降低多图场景常驻内存。
  - 回传导出流程在 `dataUrl` 缺失时可回退读取缓存，不影响功能等价。
  - 上传读取/压缩链路改为“逐张读取 + 逐张压缩”，移除 `loaded + compressed + normalized` 三份大图并存，降低峰值内存。
  - 本地/粘贴/拖拽上传完成后统一写入 `ps-cache`，后续排队跑图优先走缓存引用，减少排队任务里 Base64 的重复驻留。
  - 跑图队列快照改为“有 `psCacheId` 时不复制 `dataUrl`”，任务执行前再按需从 `ps-cache` 回填，降低排队任务对大图 Base64 的常驻占用。
  - 桥接取图的压缩阶段由并发 `Promise.all` 改为逐张串行压缩，降低多图抓取时瞬时内存峰值。
  - 活跃会话图片回读改为“分批水合”（`CHAT_IMAGE_HYDRATE_CHUNK_SIZE`），避免单次回读大量 `cacheId` 造成瞬时 Base64 峰值。
  - 控制台日志正文与修复指引新增字符上限（`LOG_MESSAGE_MAX_CHARS` / `LOG_GUIDE_MAX_CHARS`），抑制异常长报错文本导致的日志内存膨胀。
  - 上传区图片在已写入 `ps-cache` 后，会二次收敛为 UI 预览尺寸（`UPLOAD_UI_PREVIEW_MAX_SIDE`），减少上传区常驻 Base64 占用，不影响跑图链路使用缓存原图。
- 已完成（P1.3 第一阶段）
  - `chat-load` 新增 `summaryOnly` 模式：启动只加载会话摘要（`messageCount/messagesLoaded=false`），不一次性把全部消息体灌入渲染层。
  - 新增 `chat-load-session`：切换会话时按 `sessionId` 单独回读消息体，活跃会话按需加载。
  - `chat-save` 增加“未加载会话合并”策略：当渲染层会话为摘要态（`messagesLoaded=false`）时，保存不会覆盖磁盘中原消息体，避免懒加载场景下的数据丢失。
- 已完成（P1.3 第二阶段，首批）
  - 会话保存成功后，自动回收非活跃会话消息体（仅保留摘要与 `messageCount`），进一步降低长时常驻内存。
- 已完成（P1.3 第二阶段，补齐）
  - 新增会话切换节流（`CHAT_SESSION_SWITCH_DEBOUNCE_MS`），高频切换时不再立即触发多轮消息回读。
  - 新增会话图片水合节流（`CHAT_SESSION_IMAGE_HYDRATE_DEBOUNCE_MS`），避免消息流更新触发密集 cache 读取。
  - 新增非活跃会话批量回收窗口（`CHAT_SESSION_RECLAIM_WINDOW_MS`），保存成功后统一回收消息体与图片 `dataUrl`，降低频繁 setState 与 I/O 抖动。
  - 新增上述定时器的统一卸载清理，避免长时间运行后残留计时任务。
- 已完成（P2）
  - 已落地统一缓存预算策略：按 `chatRecords/images/other` 三分类执行 TTL 清理，并提供手动清理与统计。
  - 跑图多图链路已按缓存引用优先（`psCacheId`）执行，减少重复编码与重复 Base64 常驻。

## 内存策略复审（2026-02-16，第二次）
1. 会话内存策略
- 已形成“摘要常驻 + 会话体按需加载 + 非活跃回收”闭环，长会话切换不再线性抬高常驻内存。

2. 图片内存策略
- 上传图、聊天图、生成图均已具备“缓存引用优先，`dataUrl` 按需水合”的主链路。
- 运行队列与预览列表都已避免长期双持原图 Base64（保留预览所需最小集合）。

3. 调度与抖动
- 会话切换、图片水合、非活跃回收均已做窗口化调度，显著降低高频切换时的瞬时峰值与 I/O 抖动。

4. 仍需关注（非阻断）
- 开发模式（Vite HMR + source map + React Dev runtime）内存显著高于打包版，评估内存请以打包版和同场景对比为准。
- 大字号中文字体文件体积较高，主要影响包体与初次加载；若后续继续压缩内存/资源，可评估子集化字体。
