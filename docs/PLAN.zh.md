# 插件桥接方案 - 需求与设计方向（已确认）

## 目标
- 插件仅保留“连接状态 + 与 PS 联动的必要操作”。
- 所有 UI、日志、提示词、预览、任务队列等移到外部软件。
- 通信使用本地 HTTP。

## 已确认方向
- 外部软件形态：本地 Web UI（Vite/React）+ 常驻本地服务（Node/Express）
- 通信协议：HTTP（本地 127.0.0.1）
- 轮询频率：默认 50ms，失败退避 500ms，恢复成功再回 50ms

## 插件侧功能（只保留 PS 联动）
- 连接状态展示
- 一键启动/唤起外部软件
- 采集 PS 信息：
  - 选区（序列化）
  - 当前画布尺寸/分辨率
  - 当前文档ID
- 接收外部软件回传图片并导入画布
- 基本日志（连接状态/导入状态）

## 外部软件功能（UI/逻辑主阵地）
- 提示词编辑与管理
- 任务队列、历史记录
- 预览/缩略图/多图管理
- 参数面板（分辨率/比例/数量/模型）
- 日志与错误提示
- 自动导入与手动导入
- 下发 PS 指令（获取选区/导入画布/导出画布）

## UI 方向（先定基调）
- 深色主题，低对比、柔和描边
- 模块间距：24，模块内垂直间距：12
- 按钮两套样式：
  - 深灰底 + 80% 白描边 + 80% 白文字
  - 蓝色主按钮 + 白文字

## UI 结构（详细拆解）
1. 顶部栏
   - 左侧：Logo + 标题 + 版本
   - 右侧：模拟回传 / 设置

2. 预览区（在主面板内）
   - 预览占位图/提示语
   - 导出到画布按钮（蓝色）
   - 自动导入按钮（有开关态）

3. 对话框
   - 对话列表按钮
   - 聊天气泡 + 模型标签 + 时间
   - JSON提示词区块
     - 标题栏 + 复制 / 运行按钮
     - JSON内容：可编辑，随内容自增高
   - 输入框 + 发送按钮

## 对话区（独立模块：实现逻辑）
> 目标：完整拆出“聊天区”的 UI/状态/交互/滚动/数据流实现细节。

### 1) UI 结构
- 容器：`chat-panel`（独立模块，不与预览/控制台互相挤压）
- 头部：标题“与 AI 对话” + 右侧按钮（对话列表/折叠）
- 内容区：`chat-list`（可滚动）
- JSON 提示词区：`json-card`（标题栏 + 内容区 + 按钮）
- 输入区：`chat-input`（文本输入 + 发送按钮）
  - 高度基准：`480px`（可拖拽调整，需记忆）
- 上传图片区（对话区子模块）
  - 位置：输入框下方
  - 形态：主图/参考图/待添加三个方块（统一尺寸、可拖拽排序）
  - 说明：不再单独显示“上传图片”标题

### 2) 基本规则
- 布局规则：
  - 用户消息：右侧气泡（白色气泡，文字深灰）。
  - AI 消息：左侧气泡（深灰底，浅色文字）。
  - 时间戳：用户/AI 气泡旁显示时间。
  - 气泡间距：与模块内间距一致（12）。
- 消息类型：
  - `user_text`：用户输入的文字。
  - `ai_text`：聊天 API 返回文本。
  - 不新增 `system_status` / `image_notice` 消息类型；系统状态进入控制台，图片占位进入附件显示层。

### 3) 用户消息与图片附件的关系
- 用户发送消息时：
  - 消息气泡出现在右侧。
  - 消息气泡下方显示该次消息关联的图片缩略图列表（如果有）。
- 附件图片显示规则：
  - 同一条用户消息下方展示所有“已附加”图片缩略图。
  - 图片按用户选择顺序排列（支持拖拽改序）。
  - 每张图有角标标记角色（主图 / 参考图 / 仅提示词参考）。
- 仅提示词参考图：
  - 仅参与“聊天提示词拼接”。
  - 不发送给绘图 API。

### 3.1) 图片占位与发送显示（明确）
- 上传图片时：
  - 立即在聊天区插入“图片占位卡片”，卡片中心显示转圈。
  - 上传成功后，卡片替换为真实图片预览。
- 发送消息时：
  - 若该消息附带图片，则图片显示在该消息气泡下方。
  - 图片在渲染前显示转圈，加载完成替换。

### 4) 图片角色与采集按钮（主图 / 参考图 / 仅提示词参考）
- 按钮位置：输入框下方三按钮（用户点击采集）：
  - `主图`
  - `参考图`
  - `仅提示词参考`
- 按钮点击流程（统一逻辑）：
  1. 发送指令给插件：获取当前选区/画布图（具体取决于按钮逻辑）。
  2. 插件回传图片路径或 base64。
  3. UI 将图片添加到“当前输入会话附件区”，并标记角色。
  4. UI 显示缩略图，并允许拖拽排序/删除。
- 角色约束：
  - `主图` 只能 1 张（重复添加则替换）。
  - `参考图` 可多张（可排序）。
  - `仅提示词参考` 可多张（可排序）。

### 5) 跑图流程（聊天提示词 + 最后一次用户图片）
**触发方式**
- 用户点击“跑图”按钮（JSON 提示词区的按钮）。

**流程**
1. 取“最后一次用户消息”的附件图片集合：
   - 若无附件，则仅使用提示词生成。
2. 调用聊天 API，获取最终提示词（可从 AI 消息或 JSON 结构生成）。
3. 将提示词与图片组合发送给绘图 API：
   - 发送图片集合：`主图 + 参考图`（不含仅提示词参考图）。
   - 发送提示词：聊天 API 返回内容（或经过模板包装）。
4. 绘图 API 回传结果图：
   - 写入本地缓存（长期保存）。
   - 生成缩略图并缓存（每次启动可清空）。
5. UI 更新预览区显示新图；历史记录写入“生成结果列表”。

### 5.1) 异步与排队（新增：关键逻辑）
**背景约束**
- 绘图 API 同一时间只能处理一份任务。
- 用户可能在上一轮跑图未完成时继续聊天并触发下一轮跑图。
- 选区对齐依赖“当前消息对应的选区快照”，必须与任务绑定。

**核心目标**
- 跑图任务进入队列，串行执行。
- 聊天输入不阻塞，用户可继续发送消息。
- 每个任务绑定当时的选区快照与图片附件，避免错位。

**任务队列结构**
```json
{
  "queue": [
    {
      "jobId": "job-001",
      "sourceMsgId": "msg-001",
      "selectionSnapshotId": "sel-001",
      "prompt": "最终提示词",
      "images": [{ "role": "main|ref", "path": "..." }],
      "status": "pending|running|done|error"
    }
  ],
  "runningJobId": "job-001"
}
```

**入队流程**
1. 用户点击“跑图” -> 生成 `job`。
2. 记录当时的选区快照（`selectionSnapshotId`）。
3. 将 `job` 放入队列（`status=pending`）。
4. 小控制台显示“已加入队列”状态。

**执行流程（串行）**
1. 若无 `runningJobId` 且队列非空 -> 取队首执行。
2. 设置 `status=running`，小控制台显示“生成中”。
3. 调用绘图 API。
4. 成功 -> 进入回传流程（见 5.2），标记 `done`。
5. 失败 -> 记录 `error`，小控制台提示失败原因。
6. 清空 `runningJobId`，自动执行下一队列任务。

### 5.2) 回传异步流程（收到图片后的完整链路）
**步骤顺序**
1. 收到绘图结果（路径或 base64）。
2. 写入“原图保存处”（长期保存）。
3. 生成缩略图并写入“缩略图缓存”（启动可清空）。
4. UI 更新缩略图列表，预览区显示最新结果。
5. 若开启自动导出 -> 发送导出到画布指令。

**并发约束**
- 2~4 步可异步并行，但必须保证 UI 先显示“占位 + 生成中”状态。
- 导出画布必须等原图保存完成。

**错误回退**
- 原图保存失败：记录到控制台，任务标记 `error`，可重试保存。
- 缩略图失败：仍允许导出画布，但 UI 只显示占位。
- 导出失败：控制台提示，并保留“手动导出”入口。

### 5.3) 跑图按钮交互（悬浮气泡）
**目标**
- 跑图主按钮保持单一入口。
- 悬浮 0.3s 后显示二级操作，避免误触且信息清晰。

**交互规则**
1. 用户将鼠标悬浮在“跑图”按钮上 ≥ 0.3s。
2. 显示悬浮气泡（浮层，不占布局）。
3. 气泡内提供两个动作按钮：
   - `使用当前附件跑图`
   - `选择指定图片跑图`
4. 鼠标移出气泡或主按钮区域后延迟 0.2s 收起。

**文案建议（清晰化）**
- 主按钮文案：`跑图`
- 主按钮副提示（hover 或小字）：`使用上一轮提交的图片`
- 气泡按钮 1：`使用当前附件跑图`
- 气泡按钮 2：`选择指定图片跑图`

**行为说明**
- `使用当前附件跑图`：
  - 取“当前输入会话附件区”的图片（主图/参考图）。
  - 立即入队生成任务。
- `选择指定图片跑图`：
  - 打开选择框（或从历史附件列表选择）。
  - 选定后入队生成任务。
### 6) 详细实现逻辑（事件与状态）
**状态结构（前端）**
```json
{
  "chat": {
    "messages": [],
    "draftText": "",
    "attachmentsDraft": []
  }
}
```

**发送消息**
1. 用户点击发送：
   - 校验 `draftText` 或 `attachmentsDraft` 至少一项存在。
2. 组装 `user_message`：
   - `role = user`
   - `text = draftText`
   - `attachments = attachmentsDraft`
3. push 到 `messages` 列表。
4. 清空 `draftText`、`attachmentsDraft`。
5. 请求聊天 API -> 回传 `assistant_message` 插入。

**聊天区初始状态（明确）**
1. 插件/服务可用时：
   - 聊天区顶部显示 “Gemini Logo + API 连接成功”静态提示行。
2. 不在聊天区插入 `system_status` / `image_notice` 之类的系统消息气泡。
3. “系统就绪 / 连接成功 / 失败”等统一记录到小控制台与大控制台日志区。

**跑图状态显示（明确）**
- 跑图流程所有状态（开始/上传/排队/生成/完成/失败）只显示在“小控制台”。
- 聊天区不插入跑图状态气泡。
- 跑图过程中用户仍可继续聊天与发送消息，不阻塞输入。

**附件拖拽排序**
1. 用户拖拽附件缩略图。
2. 变更 `attachmentsDraft` 顺序。
3. 发送时按此顺序作为图片发送顺序。

**消息渲染**
1. 遍历 `messages`。
2. `role=user` -> 右侧白色气泡。
3. `role=assistant` -> 左侧深灰气泡。
4. 若 `attachments` 非空 -> 渲染缩略图区。

**滚动策略**
1. 新消息插入后，滚动到底部（仅当用户当前在底部附近）。
2. 用户手动上拉后，不再强制跳到底部。

### 7) 接口字段与失败回退（可直接落地）
**接口字段（建议）**
- `POST /chat/send`
  - 请求体：
    ```json
    {
      "text": "用户输入内容",
      "attachments": [
        { "role": "main|ref|prompt_only", "path": "..." }
      ],
      "meta": { "source": "ui", "ts": 1730000000000 }
    }
    ```
  - 返回体：
    ```json
    { "ok": true, "replyText": "AI 回复内容", "id": "msg-xxx" }
    ```
- `POST /images/attach`
  - 请求体：
    ```json
    { "role": "main|ref|prompt_only", "payload": { "path": "...", "base64": null } }
    ```
  - 返回体：
    ```json
    { "ok": true, "imageId": "img-xxx", "path": "..." }
    ```
- `POST /generate/run`
  - 请求体：
    ```json
    { "prompt": "最终提示词", "images": [{ "role": "main|ref", "path": "..." }] }
    ```
  - 返回体：
    ```json
    { "ok": true, "jobId": "job-xxx" }
    ```
- `GET /generate/status?jobId=...`
  - 返回体：
    ```json
    { "status": "running|done|error", "imagePath": "...", "error": "" }
    ```

**失败回退策略**
- 聊天 API 失败：
  - 不在聊天区插入系统提示气泡，仅写入小控制台与大控制台。
  - 提供“重试发送”按钮（复用原用户消息）。
- 图片附件失败：
  - UI 保留失败占位缩略图 + 可重试上传按钮。
- 绘图 API 失败：
  - UI 不在聊天区插入提示气泡，错误写入控制台。
  - 允许用户重新跑图（保留最后一次用户消息与附件）。

**修订说明**
- `system_status` 不再作为聊天消息显示，仅写入控制台。
- 聊天区初始提示以“Gemini Logo + API 连接成功”静态行呈现。

## 逻辑结构（详细拆解）
1. 指令队列（核心）
   - UI下发动作 -> /queue
   - 插件轮询 /queue/next
   - 插件执行 -> 回传 /ps/*

2. 选区联动
   - 插件获取选区序列化
   - 发送到 /ps/selection
   - 软件保存 selection，用于后续导入对齐

3. 导入画布
   - 软件发送 /ps/import
   - 插件导入到 PS
   - 若 alignSelection = true，使用保存的选区

4. 预览与缩略图
   - 软件维护缩略图列表
   - 预览仅由软件负责
   - 插件不再负责预览逻辑

5. 状态与日志
   - /status 轮询
   - UI显示连接与队列状态

## 逻辑结构（极度详细，用于验证/对照实现）
> 目标：拆到“每一步怎么走、输入输出是什么、失败怎么处理”的级别。

### 0) 启动流程
1. 外部服务启动（Node/Express）
2. Web UI 打开（浏览器或桌面壳）
3. 插件启动后开始轮询 /queue/next（50ms）
4. UI 轮询 /status 显示连接状态
5. 首次 /status ok 后显示“已就绪”

### 1) 指令队列机制（核心）
**数据结构**
- 指令对象：
  - id: cmd-xxx
  - type: string（例如 ps.getSelection）
  - payload: object
  - createdAt: timestamp

**流程**
1. UI 点击按钮 -> POST /queue {type, payload}
2. 服务入队 -> 队列长度 +1
3. 插件轮询 /queue/next
4. 若有指令 -> 返回指令并移除队列头
5. 插件执行指令
6. 插件执行成功 -> POST /ps/* 上报结果
7. UI 通过 /status 或结果回调显示完成

**失败处理**
- 插件执行失败：POST /ps/error {id, reason}
- 服务将错误写入日志队列
- UI 显示错误提示

### 2) 选区获取（ps.getSelection）
**输入**
- 指令：{ type: "ps.getSelection", payload: {} }

**执行**
1. 插件调用 PS API 获取当前选区
2. 选区序列化（格式待定）
3. POST /ps/selection {docId, selection, canvasInfo}

**输出**
- 服务缓存 selection，并记录 docId

**边界**
- 无选区：返回空 selection，并提示 UI

### 3) 画布信息获取（ps.getCanvas）
**输入**
- 指令：{ type: "ps.getCanvas", payload: {} }

**执行**
1. 插件读取画布尺寸/分辨率
2. POST /ps/canvas {docId, width, height, resolution}

### 4) 导入画布（ps.import）
**输入**
- 指令：{ type: "ps.import", payload: { path, alignSelection } }

**执行**
1. 插件读取路径文件
2. 若 alignSelection = true -> 使用缓存 selection 对齐导入
3. 导入到 PS
4. POST /ps/import {id, ok: true}

**失败**
- 文件不存在 / 读取失败 -> POST /ps/error

### 5) 预览逻辑（软件侧）
**说明**
- 插件不处理预览；预览由软件 UI 负责
- 预览图来源：服务层生成或缓存

**路径**
1. 软件接收生成任务结果（路径或 base64）
2. 写入本地缓存目录
3. UI 显示缩略图列表
4. 选择某张 -> 显示大图预览

### 6) JSON 提示词编辑
**输入**
- UI Textarea/编辑器

**执行**
1. 用户编辑 -> 本地状态更新
2. 保存/运行时发送到服务端（POST /prompt/save）
3. 服务端持久化到本地文件

### 7) 日志系统
**来源**

**流程**
1. POST /log
2. 服务存入内存队列

### 8) 自动导入

- 服务自动下发 ps.import 指令

**流程**
1. 生成结果 -> 写入缓存
2. 若 autoImport = true -> POST /queue { type: "ps.import", payload }

- 插件定时上报 /ps/heartbeat
- 服务更新 psConnected
- UI /status 展示

## 轮询策略（插件侧）
- 默认 50ms 轮询获取指令（接近无感）
- 如连续失败（超时/拒绝），退避至 500ms
- 连续成功后恢复 50ms
- 每次返回极小 JSON（单条指令或空）

## 连接状态策略（已实现）
- 服务端不再使用“只置 true 不回收”的连接标记。
- 改为心跳时间戳模型：`psLastSeenAt` + 超时窗口。
- 超时窗口：4000ms（可后续配置化）。
- 任一插件上报接口都会刷新心跳：
  - `/ps/selection`
  - `/ps/canvas`
  - `/ps/import`
  - `/ps/heartbeat`
- `/status` 返回字段：
  - `psConnected`（实时计算结果）
  - `psLastSeenAt`
  - `heartbeatTimeoutMs`

## 风险点
- UXP 插件访问本地 HTTP 的权限/限制
- 回传图片体积（base64 vs path）
- 选区序列化稳定性

## Adobe 官方约束审查（实现可行性）
> 目的：确认我们的操控逻辑在 UXP/PS 官方限制下可落地

### 1) 本地 HTTP 通信权限
- 必须使用 Manifest v5 并声明允许的域名
- `requiredPermissions.network.domains` 需要包含 `127.0.0.1`

### 2) 文件系统权限与路径
- 插件目录通常只读
- 可读写：插件 Data/Temp 目录
- 访问用户路径需要用户授权（选择目录 + token）

### 3) 图片传输策略（建议）
**优先方案：共享目录 + 文件路径**
- 软件写入固定目录（bridge_cache）
- 插件通过授权 token 读取该目录
- 优点：速度快、体积小、稳定

**备选方案：HTTP base64**
- 软件提供 base64 -> 插件写入 temp -> 导入 PS
- 缺点：大图慢、内存占用高

### 4) 导入方式
- 展示预览可用 Imaging API 输出 base64
- 正式导入建议走文件对象/路径

## Manifest v5 权限模板（草案）
```json
{
  "manifestVersion": 5,
  "requiredPermissions": {
    "network": {
      "domains": ["127.0.0.1"]
    },
    "localFileSystem": "request"
  }
}
```
